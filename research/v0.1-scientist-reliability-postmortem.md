# V0.1 ScientistPolicy reliability postmortem

## Scope and evidence

This audit uses the frozen `falsify-v0.1-prereg-4` execution plan/state, attempt journal, run ledger, public/provenance/evaluator artifacts, and the published derived `attempts.csv` and `failure_summary.csv`. It does not change evaluator scores, exclusions, or the V0.1 findings. Raw provider response bodies were not persisted; therefore an error code is not treated as proof of a more specific root cause than its artifacts support.

Across all policies/conditions, V0.1's evaluator materialization reconciles 140 attempts to 109 scientifically scored, 4 behavioral-failure scores, and 31 infrastructure-unscored attempts. ScientistPolicy's 60 attempts account for 4 behavioral and 31 infrastructure attempts; 25 attempts completed. Its 9 recovered slots ended in completed or behavioral classifications. The infrastructure-attempt count comprises 20 first-attempt failures and 11 failed retry attempts; nine additional retry attempts recovered to completed/behavioral classifications.

Recorded failure codes on ScientistPolicy attempts: `malformed_api_response` (27 infrastructure attempts) and `malformed_response` (4 scientific behavioral failures). The four behavioral slots were noisy world `8123002`, and clean worlds `8123001`, `8123002`, and `8123008`. No action-validation-invalid count was recorded for these failures: failure occurred before a proposed action was accepted.

## Classification and root-cause evidence

`malformed_response` is a **scientific behavioral failure**: the provider returned an HTTP 200 response and operational metadata, but the policy could not parse its model-generated content into the required action. For the persisted noisy example at `results/raw/8694b0b1-0dfa-45e8-9b10-141dc330ebe3/public.json`, the response finished with `length` at the 512-token limit; that attempt made two interventions before failure. This supports truncated model output for that case. Other failed response bodies were not persisted, so identical specific causes for the other three cannot be established.

`malformed_api_response` is recorded as **infrastructure delivery failure** by the contemporaneous classifier, and was retry-eligible under prereg-4. The persisted artifacts have no raw HTTP body, so they cannot establish which malformed envelope field caused these errors or whether a provider-side malformed envelope versus a client/API-envelope parsing defect occurred. Do not reinterpret these events as model-output behavior post hoc. In particular, an HTTP 200 status alone does not establish that a semantically usable structured response was received.

No independently demonstrated controller/simulator apparatus defect was found among the finalized V0.1 ScientistPolicy failures. The category `aborted` was nevertheless mapped too broadly to infrastructure in current code; it now classifies as `apparatus_failure` and cannot trigger provider retry. An apparatus failure is not a policy outcome and must invalidate/stop the affected pilot pending diagnosis.

The clean/noisy contrast is a reliability observation, not a performance contrast: noisy had 25 completions while clean had none; clean had three behavioral failures and seven terminal infrastructure slots. The records do not identify a condition-specific provider mechanism. Treat this as a severe clean-condition reliability disparity, not evidence clean observations harmed model performance.

## Retry and ledger audit

Prereg-4 allows one `-retry1` attempt only after infrastructure classification. Behavioral failures are not retried. The original and retry are separate append-only attempts under a single stable slot; slot-ledger resolution is performed after attempt rows exist. Each complete attempt starts afresh with the same world/noise identity and its own eight-intervention budget. A retry therefore can involve additional physical interventions in a failed first attempt; it is bounded recovery, not a second confirmatory logical slot. Preserve both attempts and report raw attempts separately from selected logical-slot outcomes. V0.2 must prospectively state how partial first-attempt interventions are treated and must never silently count the retry as another planned slot.

The frozen execution and analysis artifacts audit 120 logical slots separately from 140 attempts, with 20 retry attempts. They require at most two attempts per slot and reject retries after non-infrastructure classifications. No duplicate logical-slot intervention was found in the persisted state/journal/ledger reconciliation. The historical analysis remains unchanged.

## V0.2 candidate reliability gate

Candidate (not yet validated) gate: **at least 95%** of planned logical LLM treatment slots must reach a usable provider response and normal controller classification without terminal infrastructure failure. The threshold is pilot-tunable and must be frozen before DAL-156 protocol lock.

- **Denominator:** all planned logical ScientistPolicy treatment slots in the declared pilot conditions, once per slot. Report condition/environment-specific denominators too.
- **Numerator:** slots ending completed or scientifically behavioral after zero or more permitted infrastructure recoveries. Recovered infrastructure slots count as reliable completion.
- **Terminal infrastructure:** remains in denominator and is a failure. Report first-attempt infrastructure events and recovered/terminal status separately.
- **Behavioral failures:** count as normal classifications for this infrastructure-only rate, not infrastructure failures; report them separately and never retry them away.
- **Apparatus defects:** are not infrastructure delivery failures; any such defect blocks the gate pending root-cause correction and rerun of the pilot under declared rules.
- **Stratification:** report by environment, noise/measurement condition, and candidate class/model treatment. A pooled pass cannot excuse systematic infrastructure failure concentrated in a stratum; DAL-156 must define the detectable disparity rule before data collection.
- **Gate failure:** stop before confirmatory execution; diagnose and amend/re-pilot under a new protocol version. Do not proceed by excluding failed slots or tuning after inspecting treatment outcomes.

Run with `julia --project=. scripts/reliability_report_v0_2.jl EXECUTION_DIR [THRESHOLD] [OUTPUT.json]`. The command emits a stable JSON report and human-readable pass/fail line. It checks slot identity, append-only attempts, and a two-attempt bound. Example V0.1 regeneration is documented with the source artifact locations in the script invocation notes; the published V0.1 findings remain the authoritative frozen result.

## DAL-156 protocol-lock handoff

Before pilot execution, freeze: exact retry-eligible failure codes; maximum attempts (candidate: two total); whether retry is full-run restart and accounting for interventions already executed; reliability threshold; denominator and included treatments; environment/noise/candidate strata and disparity rule; abort/re-pilot behavior; and required per-attempt fields (slot/run IDs, attempt number, condition, provider/model configuration without secrets, response/envelope/parse/action/controller stages, failure code, retry basis, intervention/decision counts, timestamps/latency, and artifact references). The reliability report must run on pilot artifacts before DAL-156 locks confirmatory execution. Do not use V0.1 treatment performance to change these definitions.

## Limits

The historical API response bodies and per-decision prompt/response content are absent, preventing finer classification of the 27 `malformed_api_response` attempts and exact explanation of all four behavioral failures. The code-level category supports infrastructure classification under prereg-4, but the specific underlying provider/client root cause remains unresolved. No V0.1 scientific inclusion/exclusion decision is revised here.
